# Adding a repository or a group

Callers are generated by the `workflows` module of this repository
(`terraform/modules/workflows`, see [Terraform](Terraform.md)), applied by HCP Terraform (workspace `Github`). This page lists what to
change for a repository, and the manual prerequisites that Terraform cannot do. The module is the
reference: the variables below are those of its `variables.tf` at the time of writing.

## Steps

1. **Define the mise tasks** the groups need in the repository, merge that pull request
   ([Mise-Tasks](Mise-Tasks.md)). Terraform reads the default branch and refuses to plan otherwise.
2. **Enable the groups** for the repository in `terraform/live/projects.tf` (module input
   `workflow_groups`, below), and open a pull request there.
3. Review the plan in HCP Terraform, apply. The callers appear on the default branch of the repository.
4. Open a real pull request in the repository and check the checks run, then adjust the required status
   checks of the repository (their names are `<calling job> / <called job>`).

## Groups

| Group      | Generated callers (file names)                                                                                            | Default for             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| `core`     | `merge_group,pull_request,push.qa.yaml`, `issue_comment,pull_request.review.yaml`, `pull_request,push,schedule.scan.yaml` | all repositories        |
| `go`       | `pull_request,push.test.yaml`                                                                                             | Go modules              |
| `release`  | `workflow_dispatch.release.yaml` (`prepare` then `publish`)                                                               | Go, Pulumi              |
| `pulumi`   | `pull_request_target.codegen.yaml`, and the Pulumi `publish` job of the release caller (includes `go`)                    | Pulumi modules          |
| `security` | `schedule,workflow_dispatch.audit.yaml`                                                                                   | Go, Pulumi              |
| `issues`   | `schedule,workflow_dispatch.stale.yaml`                                                                                   | **opt-in**              |
| `oss`      | `schedule,workflow_dispatch.scorecard.yaml`, `pull_request_target.welcome.yaml`                                           | **opt-in**              |
| `e2e`      | `schedule,workflow_dispatch.e2e-sync.yaml`; the per-version callers are then created by the sync                          | explicit                |
| `wiki`     | `push,workflow_dispatch.wiki.yaml`                                                                                        | with the `wiki` feature |

The defaults per module type are the intent of the design: `go` = core + go + security + release
(+ wiki when the feature is on), `pulumi` = core + go + security + pulumi + release, `base` = core. Check the
repository's module call for what is actually enabled.

The `core.review` caller (`review`) is only generated for a repository that has an OpenRouter key
(`pr_agent_enabled`, below).

## Module inputs

| Variable           | Purpose                                                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `repository`       | Name of the target repository.                                                                                                                                     |
| `default_branch`   | Default branch (default `main`): read by the task guard, rendered in the callers' triggers, and where they are committed unless `branch` is set.                   |
| `features`         | Enabled GitHub features (`issues`, `wiki`, `projects`, `discussions`).                                                                                             |
| `branch`           | Branch the caller files are committed to; `null` = the default branch.                                                                                             |
| `workflow_groups`  | Groups to enable: `core`, `issues`, `go`, `release`, `pulumi`, `security`, `oss`, `e2e`, `wiki`.                                                                   |
| `workflows`        | Single catalog entries enabled without their group, e.g. `[{ workflow = "pulumi.codegen" }]`.                                                                      |
| `custom_workflows` | Repository-specific callers (below).                                                                                                                               |
| `publish`          | Publish job of the release caller: `"go"` or `"pulumi"`; `null` derives it from the groups.                                                                        |
| `pr_agent_enabled` | Generate the `core.review` caller. True only when the repository has an OpenRouter key.                                                                            |
| `settings`         | Per-workflow parameters (below).                                                                                                                                   |
| `commit_message`   | Commit message of caller updates, `%s` = the caller file name (default `ci(ci): Sync %s from axnic/.github-private`). It must satisfy the repository's commitlint. |

Validations that stop the plan: the `issues` group or `issues.stale` without the `issues` feature,
`core.review` requested explicitly without `pr_agent_enabled`, a malformed cron or `merge_method`, a
rendered `on:` that does not match the file name.

### `settings`

Inputs left unset are not passed: the central default applies (see each workflow page). Crons belong
to the caller, since central workflows only have `workflow_call`.

| Setting                                                  | Used by                                                          | Default                         |
| -------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------- |
| `go_paths`, `go_os`                                      | [go.test](go.test.md): path filter, input `os`                   | `["**.go", "go.mod", "go.sum"]` |
| `review_model`, `review_fallback_model`                  | [core.review](core.review.md)                                    | central defaults                |
| `scan_cron`, `scan_languages`                            | [core.scan](core.scan.md)                                        | `0 6 * * *`                     |
| `stale_cron`, `stale_days`, `stale_close_days`           | [issues.stale](issues.stale.md)                                  | `30 1 * * *`                    |
| `audit_cron`                                             | [security.audit](security.audit.md)                              | `0 6 * * *`                     |
| `scorecard_cron`, `welcome_message`                      | [oss.scorecard](oss.scorecard.md), [oss.welcome](oss.welcome.md) | `0 5 * * 1`                     |
| `pulumi_sdks`                                            | [pulumi.publish](pulumi.publish.md)                              | central default                 |
| `e2e_sync_cron`, `e2e_readme_path`, `e2e_commit_subject` | [e2e.sync](e2e.sync.md)                                          | `0 3 * * 1`                     |
| `wiki_docs_dir`                                          | [wiki.publish](wiki.publish.md)                                  | `docs`                          |

Per repository, pass the conventions of its commits: a repository whose convention is not `type(scope):`
sets `e2e_commit_subject`. Dependency updates come from Renovate: add a `renovate.json` to the repository
([Renovate](Renovate.md)); merging them is not automated.

### Workflows outside a group, and custom callers

A group is only a preset that expands into a list of workflows. Use `workflows` to enable a single one
(for example `pulumi.codegen` without the rest of `pulumi`).

`custom_workflows` generates a caller specific to a repository from a template you provide (file named
`<sorted triggers>.<action>.yaml`, same banner, same name, trigger and mise-task checks as the catalog):

```hcl
custom_workflows = [{
  action         = "integration"
  triggers       = ["pull_request"]
  template       = "${path.module}/integration.yaml.tftpl"
  name           = "Integration"
  title          = "Integration tests"
  required_tasks = ["ci:integration"]
}]
```

## PR Agent (AI review)

`core.review` needs an OpenRouter API key per repository and an allow-list of the people who may run it.
As designed in `terraform/modules/pr_agent`:

- the repository gets a **monthly budget** in USD (`pr_agent = { monthly_budget_usd = N }`, no default,
  `N > 0`): without a budget there is no key, so the `review` caller is not generated;
- Terraform creates the key (OpenRouter provider) and stores it as the repository secret
  `OPENROUTER_API_KEY`;
- the repository variable `PR_AGENT_ALLOWED_USERS` (a JSON list of logins) is computed from the
  admins and maintainers of the repository plus an extra-users list. Without it nothing runs.

The same `OPENROUTER_API_KEY` also feeds the release notes of [release.prepare](release.prepare.md) (optional).

## Manual prerequisites (outside the code)

These settings are not managed by the module and a missing one breaks a plan or a run.

1. **Terraform >= 1.9 in the `Github` workspace.** The module uses validations that refer to other
   variables.
2. **VCS trigger prefixes of the workspace** include `.github/workflows/templates/` (next to
   `terraform/`). The templates are symlinked into the module; without the prefix a change that
   touches only a template triggers no plan.
3. **The OpenRouter management key**: the sensitive workspace variable `openrouter_management_key`
   (read by the OpenRouter provider; no default, so the plan fails without it).
4. **The `axnic-bot` GitHub App** for [e2e.sync](e2e.sync.md): it pushes new files under
   `.github/workflows/`, which `GITHUB_TOKEN` can never do. The app needs `contents: write`,
   `pull-requests: write` and **`workflows: write`** on the repository, and the repository needs the
   secrets `CI_APP_ID` and `CI_APP_PRIVATE_KEY` (created by Terraform for the repositories that need the
   bot; repositories of the `e2e` group must be in that list). Without them the workflow falls back to
   `GITHUB_TOKEN` with a warning, and the push is refused.
5. **Repository setting "Allow GitHub Actions to create and approve pull requests"** for
   [e2e.sync](e2e.sync.md).
6. **The wiki enabled and initialized** (one page created by hand) for [wiki.publish](wiki.publish.md).
7. **Registries** for Pulumi providers: trusted publisher on npm and NuGet, PyPI token
   ([Releases](Releases.md)).
8. **Rulesets**: the callers are committed to the default branch, which the repository rulesets protect.
   The Terraform GitHub App must be allowed to bypass them, or the callers go through a pull request
   (`branch`).

## Adding a workflow to the catalog

1. Add the reusable workflow to this repository as `<group>.<action>.yaml` and its page `docs/<group>.<action>.md`.
2. In `terraform/`, add an entry to `terraform/modules/workflows/catalog.tf` (group, action,
   triggers, name, required tasks, permissions, inputs) and the template
   `.github/workflows/templates/<group>/<action>.yaml.tftpl`.
3. A workflow joins the group named by its `group` field: nothing else to wire.
